# MVP 오케스트레이터

아이디어에서 시작해 동작을 확인한 MVP까지 가는 흐름을 조율한다. MVP의 가치는 "작게 끝까지 동작하는 것"이므로 모든 단계가 범위를 줄이는 쪽으로 판단한다. 완료는 사람이나 에이전트의 선언이 아니라 사용자가 승인한 루브릭의 점수와 `check_done.sh`의 판정으로 정한다. 완료를 선언하는 쪽과 평가하는 쪽이 같으면 낙관으로 기울기 때문이다.

**실행 모드:** 혼합. 선행 단계는 메인 세션이 사용자와 직접 대화하고(`grilling` 스킬), 루프 단계는 서브에이전트에 순서대로 위임한다. 단계 사이의 데이터는 `_workspace/` 파일로 전달한다. 앞 결과가 다음 입력이므로 병렬로 호출하지 않는다.

## 구성

| 에이전트 | 역할 | 사용 스킬 | 출력 |
| --- | --- | --- | --- |
| mvp-planner | 범위 확정, 루브릭 초안 | mvp-scoping | `01_planner_spec.md`, `rubric.md` |
| mvp-architect | 설계와 작업 분해 | - | `02_architect_design.md`, `02_architect_tasks.md` |
| mvp-builder | 구현, 낮은 항목 수정 | mvp-build-verify | 소스 코드, `03_builder_log.md` |
| mvp-qa | 독립 평가, 점수 기록 | mvp-build-verify | `05_score.json`, `04_qa_report.md` |

판정은 `mvp-build-verify/scripts/check_done.sh`가 한다.

## 큰 구조: 루프 밖과 루프 안

- **루프 밖(선행)**: 사용자의 확인이 필요한 일. 인터뷰, 범위 확정, 루브릭 승인과 잠금. 루프 안에서는 사용자에게 물을 수 없고, 기본값으로 대신하면 확인되지 않은 가정이 기준에 굳기 때문이다.
- **루프 안(반복)**: 사용자 확인 없이 기계적으로 할 수 있는 일. 설계, 구현, 평가, 판정, 낮은 항목 수정.

## 0단계: 맥락 확인

1. `_workspace/`와 `rubric.sha256`의 유무를 본다.
   - `_workspace/`가 없으면 선행 단계부터 처음 실행한다.
   - 루브릭이 승인되어 잠겨 있고(`rubric.sha256` 있음) 일부만 고쳐 달라는 요청이면 해당 단계 이후만 실행한다. 예: "평가만 다시"는 평가와 판정만, "낮은 항목만 고쳐줘"는 수정부터.
   - "루브릭 다시 정해줘"나 "범위를 줄여서"는 선행 단계의 해당 지점부터 다시 하고, 승인 후 잠금도 다시 한다.
   - 완전히 새 아이디어면 기존 `_workspace/`를 `_workspace_{YYYYMMDD_HHMM}/`로 옮기고 처음부터 실행한다.
2. 작업 폴더에 이미 코드가 있는지 확인해 설계 단계에 알린다.
3. 지금 루프(`/goal` 또는 ralph-loop) 안인지 확인한다. `/goal`은 인자 없이 실행하면 상태가 보이고, ralph-loop는 `.claude/ralph-loop.local.md`가 있다. 루프 밖이면 루프 단계를 한 번만 실행하고 점수를 보고한 뒤 사용자에게 이어서 반복할지 묻는다. 평가자에게 넘길 반복 번호는 루프 종류와 무관하게 `_workspace/score_history.txt`의 줄 수 + 1로 정한다.

## 선행 단계 (루프 밖, 사용자와 함께)

1. **인터뷰**: `grilling` 스킬을 호출한다. 확정할 최소 항목은 누가 쓰는가, 해결하는 문제, 핵심 흐름 한 가지, 스택이나 제약, 이번에 만들지 않을 것이다. 결과를 `_workspace/00_interview.md`에 쓰고 사용자 확인을 받는다.
2. **범위와 루브릭**: `Agent(subagent_type: "mvp-planner")`에 인터뷰 파일을 넘겨 스펙과 루브릭 초안을 받는다. 포함, 제외, 성공 기준, 루브릭 항목과 가중치, 가정 목록을 사용자에게 요약해 보여준다. 사용자가 범위를 늘리자고 하면 늘어나는 만큼 무엇을 빼야 하는지 함께 제시한다.
3. **루브릭 승인과 잠금**: 사용자가 명시적으로 승인하면 `shasum -a 256 _workspace/rubric.md > _workspace/rubric.sha256`으로 잠근다. 임계값(기본 총점 85, 항목 최저 3점)도 이때 확정한다. 승인이 없으면 루프를 시작하지 않는다.
4. 사용자에게 루프 시작 명령을 안내한다 (아래 「루프 시작 명령」).

## 루프 안: 매 반복의 순서

매 반복은 처음부터 다시 시작하지 말고 파일 상태를 읽어 이어서 한다. 끝난 단계는 반복하지 않는다.

1. **잠금 확인**: `rubric.sha256`이 없으면 루프를 진행하지 말고 사용자에게 선행 단계를 먼저 끝내라고 알린다.
2. **상태에 따라 분기**
   - `02_architect_tasks.md`가 없으면 설계: `Agent(subagent_type: "mvp-architect")`.
   - 소스가 없거나 `05_score.json`이 없으면 구현: 첫 호출은 작업 목록의 1번(가장 얇은 end-to-end 조각)만 `mvp-builder`에 맡기고 실행 확인을 받은 뒤 나머지를 진행한다. 서로 독립이고 같은 파일을 건드리지 않을 때만 병렬로 호출한다.
   - 구현이 끝났으면 평가: `Agent(subagent_type: "mvp-qa")`에 반복 번호를 넘긴다. 빌더 로그 경로는 넘기지 않는다.
   - 점수가 있고 FAIL이면 수정: `mvp-builder`에 `04_qa_report.md`의 낮은 항목 개선 방향만 넘겨 그 항목과 차단 결함만 고치게 한 뒤 다시 평가한다.
3. **판정**: 평가 직후 `bash .claude/skills/mvp-build-verify/scripts/check_done.sh`를 실행하고, 출력 전문을 요약하지 말고 그대로 대화에 남긴 뒤 따른다. 이유: `/goal`의 평가 모델은 대화에 드러난 것만 읽으므로, 출력이 대화에 없으면 PASS를 확인할 수 없다.
   - PASS: 최종 보고를 한다. ralph-loop로 돌리는 중이면 같은 턴에서 방금 PASS를 확인했을 때만 마지막 줄에 완료 문구를 낸다.
   - FAIL: 출력의 가장 낮은 항목을 고친다. 이번 턴에서 계속할 수 있으면 바로 이어서 한다.
   - STUCK: `_workspace/stuck.md`에 점수 추이, 가장 낮은 항목, 시도한 수정, 의심되는 원인을 적고 정체했다고 보고한다. 성공으로 말하지 않는다. ralph-loop로 돌리는 중이면 완료 문구를 내지 않고 `ralph-loop:cancel-ralph` 스킬로 루프를 끝낸다. `/goal`에서는 종료 조건의 (2)에 해당하므로 보고하면 끝난다.
   - ERROR: 원인(루브릭 변조, 점수 누락 등)을 해결하기 전에는 판정하지 않는다. 루브릭 변조라면 누가 바꿨는지 확인하고 사용자에게 알린다. `/goal`에서는 원인을 보고하면 종료 조건의 (3)에 해당한다.
4. **대기 규칙 (ralph-loop일 때만)**: 서브에이전트를 호출한 뒤에는 턴을 끝내지 말고, 예상 산출물 파일이 생길 때까지 같은 턴 안에서 기다린다. 이유: ralph-loop는 턴이 끝날 때마다 반복을 하나 소모하는데, 에이전트를 기다리며 끝낸 턴은 진전 없이 반복만 쓴다. 이전 실행에서 반복 8회 중 2회가 이렇게 낭비됐다. 기다릴 때는 파일 존재를 확인하는 명령을 한 번에 최대 약 9분 이내로 돌리고, 시간이 넘으면 다시 확인한다. `/goal`은 서브에이전트가 실행 중이면 그 턴의 평가를 자동으로 미루므로 이 규칙이 필요 없다.

## 루프 시작 명령

선행 단계가 끝나면 사용자에게 아래 명령을 안내한다. 값은 프로젝트에 맞게 바꾼다. 기본은 `/goal`이다. 이유: `/goal`은 매 턴이 끝난 뒤 작업하는 모델과 다른 별도의 평가 모델이 종료 조건을 판정하므로 완료를 선언하는 쪽과 작업하는 쪽이 분리된다. 또 서브에이전트나 백그라운드 명령이 실행 중이면 그 턴의 평가를 자동으로 미루므로, 에이전트를 기다리다 반복만 소모하는 일이 없다.

### 기본: /goal

```
/goal mvp-orchestrator 스킬의 루프 단계를 이어서 진행한다. _workspace의 00_interview.md, 01_planner_spec.md, rubric.md, rubric.sha256은 확정되어 있다. 파일 상태를 읽어 끝난 단계는 반복하지 않고, 각 단계는 mvp-architect, mvp-builder, mvp-qa 에이전트를 Agent 도구의 subagent_type으로 호출해 맡긴다. 평가가 끝날 때마다 bash .claude/skills/mvp-build-verify/scripts/check_done.sh 를 실행하고 출력 전문을 요약하지 말고 그대로 대화에 남긴다. FAIL이면 출력의 가장 낮은 항목만 고쳐 다시 평가한다. 종료 조건: 대화에 남은 check_done.sh 출력이 (1) PASS로 시작하고 최종 보고가 있다, 또는 (2) STUCK이고 _workspace/stuck.md를 쓴 뒤 정체 사실을 보고했다, 또는 (3) ERROR이고 원인을 사용자에게 보고했다. 제약: rubric.md, rubric.sha256, score_history.txt는 수정하지 않고, 05_score.json은 mvp-qa만 쓴다. 20턴이 지나도 끝나지 않으면 현재 점수와 상태를 보고하고 멈춘다.
```

조건을 이렇게 쓰는 이유(각 부분을 지우면 약해진다):
- 평가 모델은 도구를 쓰지 못하고 대화에 드러난 것만 읽는다. 그래서 `check_done.sh` 출력 전문을 대화에 남기게 해야 한다.
- 종료 상태를 PASS, STUCK, ERROR로 나눠 적는다. STUCK과 ERROR는 성공이 아니므로 최종 보고에서 "완료"가 아니라 "정체"나 "오류"로 말한다.
- `20턴` 같은 상한은 조건 안에 넣어야 한다. `/goal`에는 별도의 최대 반복 옵션이 없다.
- `/goal`은 훅 시스템 위에서 동작하므로, 설정에서 훅이 꺼져 있거나 작업 폴더를 신뢰하지 않으면 쓸 수 없다. 이 경우 명령이 이유를 알려 준다.

### 대안: ralph-loop

`/goal`을 쓸 수 없을 때의 대안이다. 완료 판정이 완료 문구의 문자열 일치뿐이므로, 문구는 같은 턴에서 방금 PASS를 확인했을 때만 내야 한다.

```
/ralph-loop "mvp-orchestrator 스킬의 루프 단계를 이어서 진행한다. _workspace의 00_interview.md, 01_planner_spec.md, rubric.md, rubric.sha256은 확정되어 있으니 수정하지 않는다. 파일 상태를 읽어 끝난 단계는 반복하지 않고, 각 단계는 mvp-architect, mvp-builder, mvp-qa 에이전트를 Agent 도구의 subagent_type으로 호출해 맡긴다. 에이전트가 일하는 동안에는 턴을 끝내지 말고 산출물 파일이 생길 때까지 기다린다. 평가 후에는 bash .claude/skills/mvp-build-verify/scripts/check_done.sh 를 실행하고 출력이 PASS일 때만 최종 보고 후 마지막 줄에 <promise>COMPLETE</promise>를 출력한다. FAIL이면 가장 낮은 항목만 고쳐 다시 평가한다. STUCK이면 _workspace/stuck.md를 쓰고 완료 문구 없이 ralph-loop:cancel-ralph로 루프를 끝낸다." --max-iterations 10 --completion-promise "COMPLETE"
```

## 데이터 전달

모든 중간 산출물은 `_workspace/{phase}_{agent}_{artifact}.{ext}`로 저장한다. 에이전트에게는 파일 경로만 넘기고 내용을 프롬프트에 복사하지 않는다. 그래야 단계를 다시 실행할 때 같은 입력을 쓴다. 평가자에게는 빌더의 보고서 경로를 넘기지 않는다.

## 오류 처리

- 에이전트 실패는 한 번 다시 시도한다. 또 실패하면 결과 없이 진행하되 최종 보고에 누락을 적는다.
- 사용량 한도, 인증 만료, 권한 거부는 다시 시도하지 않는다. 부분 산출물을 직접 열어 어디까지 됐는지 확인하고 사용자에게 보고한다.
- 에이전트의 판단을 추측해 채우지 않는다. 직접 확인한 사실만 반영한다.
- 평가자가 환경 문제로 점수를 매기지 못하면 점수 파일이 없으므로 `check_done.sh`가 FAIL을 낸다. 점수를 임의로 채우지 않는다.
- 빌더가 루브릭이 부당하다고 제안하면 사용자에게 전달한다. 오케스트레이터가 루브릭을 고쳐 통과시키지 않는다.

## 최종 보고

사용자에게 다음을 알린다. 만든 것(핵심 흐름), 실행하는 방법, 항목별 점수와 총점 추이(`score_history.txt`), 의도적으로 뺀 것, `unverified` 항목, 다음에 붙일 만한 기능 후보. 최종 산출물은 프로젝트 디렉터리에 두고 `_workspace/`는 검증 기록으로 남긴다.

## 테스트 시나리오

- 정상 흐름: 인터뷰와 루브릭 승인 후 `/goal`을 시작한다. 반복 1에서 설계, 구현, 평가가 끝나 총점 72로 FAIL이 나오고, 반복 2에서 가장 낮은 항목(robustness)만 고쳐 재평가하면 총점 90, 차단 0, 항목 최저 4로 PASS가 나온다. PASS 출력과 최종 보고가 대화에 남으면 평가 모델이 조건 충족으로 판정해 끝난다.
- 정체 흐름: 반복 2와 3에서 총점이 60, 60, 60으로 오르지 않으면 `check_done.sh`가 STUCK을 출력한다. `stuck.md`를 쓰고 정체했다고 보고한다. `/goal`에서는 조건 (2)로 끝나고, ralph-loop에서는 완료 문구 없이 루프를 취소한다.
- 대기 흐름: `/goal`에서 서브에이전트가 일하는 동안 턴이 끝나도 평가가 미뤄져 반복(턴)이 소모되지 않는다. ralph-loop에서는 대기 규칙대로 같은 턴에서 파일을 기다린다.
- 변조 흐름: 빌더가 루브릭 파일을 수정하면 `check_done.sh`가 ERROR를 출력한다. 판정하지 않고 사용자에게 알린다.
- 후속 흐름: "평가만 다시 돌려줘"는 잠금을 확인한 뒤 평가와 판정만 실행한다. "낮은 항목만 고쳐줘"는 `04_qa_report.md`를 읽고 수정부터 한다.
