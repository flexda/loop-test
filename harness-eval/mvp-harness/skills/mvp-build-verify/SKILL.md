# MVP 구현과 점수 평가

실행해 보기 전의 코드는 가설일 뿐이다. 구현은 작게 나누고 매 단계 실행으로 확인한다. 평가는 구현한 쪽과 분리하고 점수로 남겨, 기준에 못 미치면 어느 항목이 얼마나 못 미치는지가 다음 반복의 방향이 되게 한다.

## 구현 절차 (builder)

1. 작업 목록의 1번 작업은 핵심 흐름이 입력에서 출력까지 한 번 통과하는 가장 얇은 조각이다. 화면이나 기능을 다듬지 말고 먼저 관통시킨다.
2. 작업을 시작하기 전에 필요한 도구가 있는지 `which`로 확인한다. 설치했다면 설치 후 실제 경로를 확인한다. 경로를 가정하지 않는다.
3. 구현한 뒤 반드시 실행한다. 서버면 띄워서 요청을 보내고, CLI면 명령을 돌리고, 라이브러리면 호출한다. 실행한 명령과 출력을 로그에 남긴다.
4. 실패하면 원인을 읽고 한 번 고쳐 다시 실행한다. 같은 오류가 두 번 반복되면 멈추고 보고한다. 테스트를 약하게 바꾸거나 오류를 숨겨 통과시키지 않는다.
5. 파이썬은 `uv`를 쓴다. 실행 방법(설치, 시작 명령)은 README에 적는다.
6. 범위 밖 기능이 떠오르면 만들지 말고 로그의 "제안"에 적는다.
7. 수정 호출에서는 `04_qa_report.md`의 가장 낮은 항목과 차단 결함만 고친다. 점수가 이미 높은 부분을 건드리면 오히려 내려갈 수 있다.
8. `rubric.md`, `rubric.sha256`, `05_score.json`, `score_history.txt`는 수정하지 않는다. 기준이나 점수를 바꾸면 평가가 의미를 잃기 때문이다.

## 평가 절차 (qa)

1. `_workspace/rubric.md`를 읽는다. 빌더의 로그(`03_builder_log.md`)는 읽지 않는다. 같은 가정을 공유하면 오류를 못 보기 때문이다.
2. 항목마다 점수를 매긴다. `script` 항목은 명령을 실행한 결과로, `judge` 항목은 루브릭의 3점, 5점 기준과 대조해 근거를 적는다.
   - `functional`: 스펙의 성공 기준을 한 줄씩 실행한다. 앱을 처음부터 문서대로 띄워 본다. 문서대로 안 되면 그것이 첫 번째 결함이다.
   - 경계면을 교차 확인한다. 저장 후 읽기, 입력 형식과 파서, 서버 응답과 화면 표시처럼 데이터가 넘어가는 곳에서 양쪽 형식을 나란히 읽는다. 파일이 있다는 사실만으로 통과시키지 않는다.
   - 흔한 이상 입력(빈 입력, 중복)을 한두 개만 시험한다. 광범위한 예외 탐색은 MVP의 범위가 아니다.
3. 차단 결함(핵심 흐름이 끊기는 것)의 개수를 센다. 일반 결함은 점수에 반영하고, 참고 결함은 보고서에만 적는다.
4. 직접 실행하지 못한 항목은 점수 근거로 쓰지 않고 `unverified`에 적는다. 대체 방법을 썼다면 대체했다고 근거에 명시한다.
5. `_workspace/05_score.json`을 쓴다 (형식은 `mvp-scoping/references/rubric-template.md`). 합계는 적지 않는다.
6. `_workspace/04_qa_report.md`에 항목별 근거, 결함과 재현 방법, 미확인 항목을 쓰고, 점수가 가장 낮은 항목마다 무엇을 고치면 오르는지 적는다.

## 판정 (오케스트레이터)

평가가 끝나면 `scripts/check_done.sh`를 실행한다. 판정은 이 스크립트의 출력이 전부다.

| 출력 | 의미 | 다음 행동 |
| --- | --- | --- |
| PASS | 총점이 기준 이상이고 차단 결함이 없고 모든 항목이 최저점 이상 | 최종 보고 후 완료 문구 출력 |
| FAIL | 기준 미달 | 출력에 나온 가장 낮은 항목을 빌더가 고치고 재평가 |
| STUCK | 점수가 2회 연속 오르지 않음 | `_workspace/stuck.md`에 원인과 시도 내용을 적고 멈춤 |
| ERROR | 루브릭 변조, 점수 누락, jq 없음 등 | 원인을 해결하기 전에는 판정하지 않음 |

스크립트가 점수를 직접 합산하므로 평가자가 합계를 적지 않는다. 판정을 사람이나 에이전트의 판단에 맡기면 완료를 낙관하는 쪽으로 기울기 쉽다.

## 보고서 형식

QA 보고서에는 항목별 점수와 근거, 등급별 결함(재현 방법 포함), 미확인 항목, 낮은 항목의 개선 방향을 쓴다. 빌더 로그에는 작업 번호 또는 반복 번호별로 한 일, 실행한 명령, 결과, 제안을 쓴다.
