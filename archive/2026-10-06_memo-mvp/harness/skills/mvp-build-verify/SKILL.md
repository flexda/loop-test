# MVP 구현과 검증

실행해 보기 전의 코드는 가설일 뿐이다. 이 스킬은 구현을 작게 나누고 매 단계 실행으로 확인해, 마지막에 한꺼번에 무너지는 일을 막는다.

## 구현 절차 (builder)

1. 작업 목록의 1번 작업은 핵심 흐름이 입력에서 출력까지 한 번 통과하는 가장 얇은 조각이다. 화면이나 기능을 다듬지 말고 먼저 관통시킨다.
2. 작업을 시작하기 전에 필요한 도구가 있는지 `which`로 확인한다. 설치했다면 설치 후 실제 경로를 확인한다. 경로를 가정하지 않는다.
3. 구현한 뒤 반드시 실행한다. 서버면 띄워서 요청을 보내고, CLI면 명령을 돌리고, 라이브러리면 호출한다. 실행한 명령과 출력을 로그에 남긴다.
4. 실패하면 원인을 읽고 한 번 고쳐 다시 실행한다. 같은 오류가 두 번 반복되면 멈추고 보고한다. 테스트를 약하게 바꾸거나 오류를 숨겨 통과시키지 않는다.
5. 파이썬은 `uv`를 쓴다. 실행 방법(설치, 시작 명령)은 README에 3줄 이내로 적는다.
6. 범위 밖 기능이 떠오르면 만들지 말고 로그의 "제안"에 적는다.

## 검증 절차 (qa)

1. 스펙의 성공 기준을 표로 옮긴다. 열은 기준, 실행 방법, 기대 결과, 실제 결과, 판정이다.
2. 앱을 처음부터 실행 방법 문서대로 띄운다. 문서대로 안 되면 그것이 첫 번째 결함이다.
3. 성공 기준을 한 줄씩 실행한다. 직접 실행하지 못한 기준은 "미확인"으로 두고 이유를 쓴다.
4. 경계면을 교차 확인한다. 저장 후 읽기, 입력 형식과 파서, 서버 응답과 화면 표시처럼 데이터가 넘어가는 곳에서 양쪽 형식을 나란히 읽는다. 파일이 있다는 사실만으로 통과시키지 않는다.
5. 핵심 흐름을 끝까지 한 번 통과시킨 뒤, 빈 입력이나 중복 같은 흔한 이상 입력을 한두 개만 시험한다. 광범위한 예외 탐색은 MVP의 범위가 아니다.
6. 결함은 등급으로 나눈다. 차단은 핵심 흐름이 끊기는 것, 일반은 성공 기준과 어긋나는 것, 참고는 개선 제안이다.

## 보고서 형식

QA 보고서에는 판정 표, 등급별 결함(재현 방법 포함), 미확인 항목, 전체 판정(통과, 조건부 통과, 실패)을 쓴다. 빌더 로그에는 작업 번호별로 한 일, 실행한 명령, 결과, 제안을 쓴다.
