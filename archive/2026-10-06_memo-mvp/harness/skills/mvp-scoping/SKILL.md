# MVP 범위 확정

MVP는 가설 하나를 검증할 만큼만 만든 제품이다. 기능이 많으면 만드는 시간이 늘고 무엇이 가치를 만드는지 흐려지므로, 빼는 판단이 더하는 판단보다 중요하다.

## 절차

1. **가설 한 줄**: "누가 ~하면 ~할 것이다" 형태로 쓴다. 쓰지 못하면 인터뷰가 부족한 것이므로 질문 목록을 돌려보낸다.
2. **핵심 흐름 하나**: 사용자가 가치를 얻는 처음부터 끝까지의 단계를 3~6단계로 쓴다. 여러 흐름이 후보면 가설 검증에 가장 직접적인 것 하나만 고른다.
3. **기능 후보 판정**: 인터뷰에 나온 기능을 모두 나열하고 각각 판정한다.
   - 포함: 없으면 핵심 흐름이 끊긴다. 끊기는 이유를 한 줄로 적는다.
   - 제외: 있으면 좋지만 흐름은 된다. 제외 이유를 적는다.
   - 나중: 가설이 맞으면 필요해질 것. 목록에만 둔다.
4. **대체 수단 확인**: 포함 기능마다 "수작업이나 하드코딩으로 대신해도 가설 검증이 되는가"를 묻는다. 되면 제외로 바꾼다. 로그인 대신 고정 사용자, 결제 대신 안내 문구 같은 식이다.
5. **성공 기준**: 핵심 흐름의 단계마다 실행으로 확인할 수 있는 문장을 쓴다. "빠르다"나 "직관적이다"처럼 실행으로 확인할 수 없는 표현은 쓰지 않는다.
6. **가정 목록**: 인터뷰에서 확인하지 못해 가정한 것을 따로 모은다. 가정이 성공 기준을 바꾸면 사용자 확인이 필요하다고 표시한다.

## 스펙 문서 형식

```
# MVP 스펙: {이름}
## 가설
## 핵심 흐름 (번호 순서)
## 포함 기능 (기능 - 없으면 끊기는 이유)
## 제외 기능 (기능 - 제외 이유)
## 나중에
## 성공 기준 (실행으로 확인 가능한 문장)
## 가정 (확인 필요 여부 표시)
```

## 판단 기준

포함 기능이 6개를 넘으면 범위가 큰 것이다. 핵심 흐름을 다시 좁힌다. 사용자가 범위를 늘리길 원하면 막지 말고, 늘어나는 항목마다 대신 뺄 것을 함께 제시한다.
