# MVP 오케스트레이터

아이디어에서 시작해 동작을 확인한 MVP까지 가는 흐름을 조율한다. MVP의 가치는 "작게 끝까지 동작하는 것"이므로 모든 단계가 범위를 줄이는 쪽으로 판단한다.

**실행 모드:** 혼합. 1단계는 메인 세션이 사용자와 직접 대화하고(`grilling` 스킬), 2~5단계는 서브에이전트에 순서대로 위임한다. 단계 사이의 데이터는 `_workspace/` 파일로 전달한다. 단계마다 앞 결과가 다음 입력이므로 병렬로 호출하지 않는다.

## 구성

| 에이전트 | 역할 | 사용 스킬 | 출력 |
| --- | --- | --- | --- |
| mvp-planner | 범위 확정 | mvp-scoping | `01_planner_spec.md` |
| mvp-architect | 설계와 작업 분해 | - | `02_architect_design.md`, `02_architect_tasks.md` |
| mvp-builder | 구현 | mvp-build-verify | 소스 코드, `03_builder_log.md` |
| mvp-qa | 검증 | mvp-build-verify | `04_qa_report.md` |

## 0단계: 맥락 확인

1. `_workspace/`가 있는지 본다.
   - 없으면 1단계부터 처음 실행한다.
   - 있고 사용자가 일부만 고쳐 달라고 하면 해당 단계 이후만 다시 실행한다. 예: "QA만 다시"는 5단계만, "범위를 줄여서"는 2단계부터.
   - 있고 완전히 새 아이디어면 기존 `_workspace/`를 `_workspace_{YYYYMMDD_HHMM}/`로 옮기고 처음부터 실행한다.
2. 작업 폴더가 비어 있는지, 이미 코드가 있는지 확인해 설계 단계에 알린다.

## 1단계: 인터뷰 (메인 세션)

`grilling` 스킬을 호출해 아이디어를 인터뷰한다. 확정해야 할 최소 항목은 누가 쓰는가, 해결하는 문제, 핵심 흐름 한 가지, 쓰고 싶은 스택이나 제약, 이번에 만들지 않을 것이다. 사용자가 이미 충분히 구체적으로 말했다면 남은 항목만 묻는다. 결과를 `_workspace/00_interview.md`에 정리하고 사용자 확인을 받는다. 사용자 확인 없이 다음 단계로 넘어가지 않는다.

## 2단계: 범위 확정

`Agent(subagent_type: "mvp-planner")`에 인터뷰 파일 경로를 넘긴다. 반환된 스펙의 포함·제외 목록과 성공 기준을 사용자에게 요약해 보여주고 확인받는다. 사용자가 범위를 늘리자고 하면 늘어나는 만큼 무엇을 빼야 하는지 함께 제시한다.

## 3단계: 설계

`Agent(subagent_type: "mvp-architect")`에 스펙 경로를 넘긴다. 스택에 새 도구 설치가 필요하거나 스펙에 없는 구성요소(인증, 결제, 배포 등)를 넣어야 한다고 보고하면 사용자에게 확인한다.

## 4단계: 구현

작업 목록을 순서대로 `Agent(subagent_type: "mvp-builder")`에 맡긴다. 첫 호출은 목록의 1번 작업(가장 얇은 end-to-end 조각)만 맡기고 실행 확인을 받은 뒤 나머지를 진행한다. 작업이 서로 독립이고 같은 파일을 건드리지 않을 때만 병렬로 호출한다.

## 5단계: 검증과 수정 루프

1. `Agent(subagent_type: "mvp-qa")`로 검증한다.
2. 차단 또는 일반 결함이 있으면 `mvp-builder`에 QA 보고서를 넘겨 고치고 QA를 다시 돌린다. 최대 2회까지 반복한다.
3. 2회 후에도 차단 결함이 남으면 멈추고 남은 결함과 원인 후보를 사용자에게 보고한다. 더 시도할지는 사용자가 정한다.

## 6단계: 최종 보고

사용자에게 다음을 알린다. 만든 것(핵심 흐름), 실행하는 방법(명령), 성공 기준별 통과 여부, 의도적으로 뺀 것, 미확인 항목, 다음에 붙일 만한 기능 후보. 최종 산출물은 프로젝트 디렉터리에 두고 `_workspace/`는 검증 기록으로 남긴다. 끝으로 `CLAUDE.md`의 변경 이력을 갱신할 내용이 있는지 확인한다.

## 데이터 전달

모든 중간 산출물은 `_workspace/{phase}_{agent}_{artifact}.{ext}`로 저장한다. 에이전트에게는 파일 경로만 넘기고 내용을 프롬프트에 복사하지 않는다. 그래야 단계를 다시 실행할 때 같은 입력을 쓴다.

## 오류 처리

- 에이전트 실패는 한 번 다시 시도한다. 또 실패하면 결과 없이 진행하되 최종 보고에 누락을 적는다.
- 사용량 한도, 인증 만료, 권한 거부는 다시 시도하지 않는다. 부분 산출물을 직접 열어 어디까지 됐는지 확인하고 사용자에게 보고한다.
- 에이전트의 판단을 추측해 채우지 않는다. 직접 확인한 사실만 반영한다.
- 스펙과 구현이 충돌하면 어느 쪽을 따를지 사용자에게 묻는다.

## 테스트 시나리오

- 정상 흐름: "메모를 저장하고 목록으로 보는 간단한 웹 앱 MVP 만들어줘". 인터뷰에서 핵심 흐름을 "메모 추가 후 목록 확인"으로 확정하고, 스펙의 제외 목록에 로그인과 검색이 오르며, 구현 후 QA가 성공 기준 전부를 실행해 통과로 판정한다.
- 오류 흐름: QA가 "추가한 메모가 새로고침 후 사라짐"을 차단 결함으로 보고하면 빌더가 고치고 QA를 다시 돌린다. 2회 후에도 남으면 사용자에게 보고하고 멈춘다.
- 후속 흐름: "QA만 다시 돌려줘"는 `_workspace/`를 읽고 5단계만 실행한다.
